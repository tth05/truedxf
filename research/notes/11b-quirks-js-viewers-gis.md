# 11b — Real-world quirks from JS viewers, JS/C# parsers and GIS/CAD importers

Mined from the GitHub dumps in `research/github/raw/`:

- JS/TS viewers and parsers: vagran/dxf-viewer, gdsestimating/dxf-parser + three-dxf, bjnortier/dxf, dotoritos-kim/dxf-json, mlightcad/cad-viewer + realdwg-web
- Writers and C#: tarikjabiri/dxf (a TS writer), ixmilia/dxf (C#)
- DXF-filtered searches: OSGeo/gdal (OGR DXF driver), FreeCAD, QGIS

About 1,100 threads were read in full after title triage. Group-code claims were checked against the attached sample files where marked "sample-checked". This note is a companion to the ezdxf/ACadSharp/LibreCAD quirk notes and does not repeat spec basics.

**Citation style.** `dxf-viewer#36`, `three-dxf#24`, `dxf-parser#64`, `bjnortier-dxf#142`, `tarikjabiri-dxf#74`, `dxf-json#94`, `ixmilia-dxf#110`, `cad-viewer#473`, `realdwg-web#pr173` (`#prN` marks a PR where issue and PR numbers could clash), `gdal#1011`, `freecad#8704`, `qgis#47381`.

**Confidence tags.**

- **VERIFIED-BY-ACAD**: someone opened or compared the file in AutoCAD, TrueView or an Autodesk viewer and said so in the thread. Nobody in these threads compared against AutoCAD *PLOT*. They compared screen display, or whether AutoCAD accepted or rejected the file.
- **REPORTED**: a claim by a user or maintainer.
- **ASSUMPTION**: my own inference.
- **UNKNOWN / needs AutoCAD test**: marks items for the test backlog.

**Caveat about ground truth.** The dxf-viewer maintainer's ground truth is the *Autodesk online viewer*. cad-viewer mixes AutoCAD desktop, AutoCAD Web and TrueView. Several threads show the Autodesk viewers differ from AutoCAD PLOT on these points:

- no-plot layers (cad-viewer#167, #338)
- hatch pattern scale and angle (dxf-viewer#36)
- ACI-7 fills (cad-viewer#426)

Treat "matches Autodesk viewer" as weaker evidence than "matches AutoCAD plot".

## 1. Tokenizer and file-level robustness

Every item below broke at least one reader.

**Line and number format**

- **`999` comment pairs can appear anywhere**:
  - before the first `0 SECTION`: DG Nest R12 (bjnortier-dxf#143); LibreCAD `999 dxfrw 0.6.3`; netDxf `999 DXF file generated by netDxf`; FreeCAD `999 FreeCAD v0.22`;
  - inside every section: PowerPCB/Mentor PADS (bjnortier-dxf#145, sample-checked).
  - Drop them in the tokenizer, not per section (freecad#16131). REPORTED
- **Group codes may be unpadded** (`5`, `330`; netDxf, PowerPCB) or padded (`62=  256`, LibreCAD). **Trim codes and numeric values.** REPORTED (dxf-parser#109, bjnortier-dxf#145)
- **Line endings.** Expect CRLF, LF, `\r\r\n` and a lone `\r`.
  - `std::getline` on Linux left a trailing `\r` in values (freecad#19247).
  - A code/value desync `{code: NaN, value:'310'}` is still unexplained, possibly caused by extra empty lines (dxf-parser#102, open).
  - An extra trailing newline after `EOF` broke ixmilia (ixmilia-dxf#70). REPORTED
- **UTF-8 BOM** (0xFEFF) at the start gave "Not a valid DXF file header" (ixmilia-dxf#196). Strip it. REPORTED
- **Float formats seen**:
  - German decimal comma `2,5` from a writer that used the current culture, while code 42 in the same record was `2.5` (ixmilia-dxf#110);
  - `1.000000000000000E 20`, with a space instead of `+` in the exponent (ixmilia-dxf#169);
  - `inf.0`, `-inf.0`, `nan.0` from QGIS (qgis#22140, #54176).
  - Parse leniently, never with the host culture (ixmilia-dxf#36: `2456478.590142998` was read as `2456478590142998` under a German locale). Map NaN/Inf to "missing". REPORTED

**Header variables and long lines**

- **Header variable types can differ from the spec.** `$ACADMAINTVER` is written as **90** (not 70), with values > int16. This comes from AutoCAD Plant 2019, a "2007" file with an AC1032 header, and MicroStation (ixmilia-dxf#88, #92, pr8). Take the type from the group code actually present. VERIFIED-BY-ACAD (AutoCAD-written files)
- **Header variables with the group-code line missing entirely.** LibreDWG `dwg2dxf` writes `9 $DIMPOST` followed by an empty line and no code. The same happens for about 12 DIM* block variables, LTYPE 3 and STYLE (freecad#19247, 35 MB DesignRumah.dxf). The reader needs a resync strategy rather than an abort. REPORTED
- **Repeated header variables.** `$CUSTOMPROPERTYTAG`/`$CUSTOMPROPERTY` appear once per property, so keep them as a list (dxf-parser#22). An empty `$FINGERPRINTGUID` was seen in a .CDX-derived file (ixmilia-dxf#83). REPORTED
- **Lines longer than 255 characters exist** even though the R12 spec says DXFIN fails on them:
  - `$CUSTOMPROPERTY` with more than 2000 hex characters, from ODA-converted MicroStation DGN (gdal#3828);
  - XDATA 1000 strings of 256+ characters, from ODA Drawings Explorer; DWG TrueView 2018 opens that file (gdal#8527);
  - MLEADER 304 text (gdal#pr3909).
  - Never cap line length. VERIFIED-BY-ACAD (TrueView 2018 opens the gdal#8527 file)

**Code order and pair consumption**

- **Point codes can interleave**: `10,11,12,20,21,22` in a Thingiverse laser file (dxf-parser#64). Revit puts `1001 REVIT` right after the 3DFACE 13/23/33 codes, which dropped the 4th vertex (dxf-parser#112).
  - Tokenize a whole entity, up to the next `0`, into subclass-aware slots, then interpret.
  - Do not use a one-pair-rewind scanner. dxf-parser shipped several bugs from this: LWPOLYLINE swallowed 210, vertex loops ate the entity-level 210 (dxf-parser#23, #47).
  - REPORTED
- **One generic (code, value) pair reader plus dispatch.** A deepnest file put the FreeCAD C++ reader out of sync for good because one common code (8) was unhandled in one entity reader (freecad#6924, #11701). REPORTED
- **Unknown group codes must be skipped, not abort the entity or the file.**
  - CLO 3D writes a non-standard **250** in POLYLINE of an AC1006 file (ixmilia-dxf#106).
  - AutoCAD writes **380** (plot style type) and **347** (material) on INSERT; dxf-json dropped everything after 380 (dxf-json#86).
  - dxf-json#94 is a related case of undocumented codes.
  - REPORTED
- **The same code can mean different things in different subclasses, or repeat.**
  - ATTRIB/ATTDEF carry `280` twice (dxf-parser#118, sample-checked).
  - MTEXT `50` means both rotation and column heights (ixmilia-dxf#184).
  - HATCH `10` is the elevation point, then seed points, then edge data (dxf-viewer#36).
  - LWPOLYLINE `210` is written twice, before and after the vertices (tarikjabiri-dxf#74 samples); let the last one win.
  - The model must be subclass-aware and position-aware. REPORTED
- **Where group codes sit matters to AutoCAD (writer side), but readers must be lenient.**
  - GDAL wrote `8` before `100 AcDbEntity`. AutoCAD and BricsCAD read it; ezdxf ignored the layer (gdal#2348).
  - mozman: ARC with 50/51 in the AcDbCircle subclass instead of AcDbArc makes AutoCAD refuse the file (gdal#2348).
  - VERIFIED-BY-ACAD (mozman's test)

**Malformed data and parser hardening**

- **Malformed XDATA.** A `1002 {` where `}` was expected made ixmilia nest and swallow the rest of the file. **AutoCAD and QCAD ignore it and load everything.** Close all XDATA state at the next `0` (ixmilia-dxf#166). VERIFIED-BY-ACAD (per reporter)
  - Also seen: a point missing 1010 with 1020/1030 present (ixmilia-dxf#74), and several XDATA apps on one entity: `ACAD` DSTYLE plus `ACAD_DSTYLE_DIMRADIAL_EXTENSION` (dxf-json#100). REPORTED
- **`102` groups.**
  - Several `{...}` groups on one record (`{ACAD_REACTORS` + `{ACAD_XDICTIONARY`) broke dxf-json BLOCK_RECORD parsing, and the block name was lost (dxf-json#145, cad-viewer#132).
  - SketchUp 2016 writes **102 as data** (`102 VTR_0.000_…_GRIDDISPLAY`) inside XRECORD, not as `{` groups (ixmilia-dxf#61).
  - REPORTED
- **Fuzzers find crashes in line buffering** (gdal#3936, #pr4188). Other hazards: CRLF split across read buffers (gdal#pr6080); self-including blocks (gdal#pr252, *"the test DXF file crashes AutoCAD upon opening"*). Guard INSERT recursion. VERIFIED-BY-ACAD (AutoCAD crashes on the self-insert)
- **Tolerate malformed entities and count them.** One CIRCLE with a negative radius aborted a whole 100k-entity read (realdwg-web#pr171, ezdxf `circle_radius_le_0.dxf`). Report `malformedEntityCount` and `unknownEntityCount`. REPORTED
- **A POLYLINE with no VERTEX/SEQEND**, followed directly by `0 LINE` (5× in an AC1032 file, 37 POLYLINE vs 32 SEQEND), hung dxf-viewer forever (dxf-viewer#166). Any loop "until SEQEND" must also stop at the next non-VERTEX entity. REPORTED
- **Never `eval` or interpolate DXF strings into code.** A `"` in text broke FreeCAD, which generated Python source (freecad#11408). REPORTED

**Non-DXF input and limits**

- **What arrives as ".dxf" is not always ASCII DXF.** Of 53,000 laser-shop DXFs, 180 failed in ixmilia (ixmilia-dxf#110):

  | Failures | Cause |
  |---|---|
  | 111 | post-R13 **binary DXF** |
  | 63 | actually **DWG** |
  | 3 | decimal commas |
  | 1 | truncated `\U+` |
  | 1 | truncated file |
  | 1 | empty file |

  - Also seen: an HTTP error page (dxf-viewer#13) and base64 data URLs (dxf-parser#44).
  - Some corpus attachments are GitHub HTML pages; see the sample table.
  - Sniff the input: `AutoCAD Binary DXF\r\n\x1a\0` for binary, `AC10xx` magic for DWG, `<!DOCTYPE`/`<html` for HTML. REPORTED
- **Binary DXF is rare but real.**
  - Producers: DraftSight, AutoCAD, BricsCAD, ODA converter (gdal#pr12688).
  - R12 binary samples: bjnortier-dxf#137 `joedj261.dxf` (AC1009, 9 KB), StaticBoot3-R14.
  - "A few among thousands" of user uploads; about 25% smaller than ASCII (bjnortier-dxf#29, #31).
  - R12 uses 1-byte group codes, R13+ uses 2-byte; 310/1004 are binary chunks (dxf-json#pr154).
  - REPORTED
- **V8 string limit.** A 1.1 GB file hit "Invalid string length" via `dxfString += chunk` (dxf-parser#49). dxf-viewer buffers the whole file as one string (~1 GB ceiling); files with OLE objects can be huge (dxf-viewer#36, #95). REPORTED
  - dxf-json's AsyncIterator streaming parser was **>5× slower** (dxf-json#3). Use a synchronous inner loop over `Uint8Array` chunks.
  - Replacing a regex split with `indexOf` scanning made parsing about 24× faster (dxf-parser#pr117).
- **Handles can exceed 2^53.** `$HANDSEED D9B071D01A0CB6A8` (dxf-json `sample_A_000217.dxf`) made `number` increments no-ops. The result was an infinite loop and a frozen tab, taking more than 5 min before the fix and 175 ms after (realdwg-web#pr178). Keep handles as strings or BigInt. REPORTED
- **JS engine limits.**
  - `arr.push(...entities)` / `push.apply` with more than 150k entities throws `RangeError: Maximum call stack size exceeded` (realdwg-web#pr179, cad-viewer#34, #308).
  - Object graphs with owner back-pointers break `JSON.stringify` (dxf-json#8, #13).
  - REPORTED

## 2. Version, dialect and structural variety

- **ENTITIES-only files, or files with no HEADER/TABLES**, come from:
  - OpenSCAD: BLOCKS + ENTITIES, 452 LINE, no handles (bjnortier-dxf#34, sample-checked);
  - Italian cadastral maps: `G267_000100.DXF` with no HEADER at all (qgis#17760; CAD programs load it with a warning);
  - KiCad: HEADER holds only `$ANGBASE`, `$ANGDIR`, `$MEASUREMENT` (freecad#10554, #15732).
  - Default everything. REPORTED
- **No `100` subclass markers** in R12 (AC1009) files or minimal writers. This includes **DWG TrueView 2027's own samples** `bridge`, `cube` and `diamond`.
  - realdwg-web's reader swallowed the geometry codes into the common-entity loop, and those drawings opened blank (realdwg-web#pr172).
  - VERIFIED-BY-ACAD (Autodesk-shipped samples)
- **R12 has no HATCH.** AutoCAD's R12 export writes hatches as anonymous `*X<n>` blocks of LINE/SOLID (bjnortier-dxf#114, `0607_B.dxf`, sample-checked). Anonymous `*X`/`*U`/`*D`/`*A`/`*T` blocks must render through their INSERT or owner. REPORTED
- **`$ACADVER` can be absent or wrong.**
  - PowerPCB and KiCad write no `$ACADVER`.
  - tarikjabiri wrote AC1009 with R2000 structure (tarikjabiri-dxf#186).
  - QGIS declared AC1015 but used 420/440 (qgis#60802). Those codes arrive in the AC1018 (R2004) reference.
  - Detect the dialect from structure; do not gate parsing on the declared version. REPORTED
- **Handles are optional.**
  - OnShape omits code 5 on BLOCK/ENDBLK and tables. It uses `$MODEL_SPACE`/`$PAPER_SPACE` names and writes no `AcDbBlockEnd` (dxf-parser#3, #6).
  - A handle-less VPORT `*ACTIVE` appears in a hand-written file; AutoCAD requires the handle there (cad-viewer#101).
  - **Never key maps by handle alone.** Synthesise handles. REPORTED
- **Handle collisions across tables.** Layer PLATE and STYLE Standard both had handle `11` (cad-viewer#420). Invented default objects collided with imported handles (realdwg-web#pr132). Key by (table, handle) and honour `$HANDSEED`. REPORTED
- **Missing LAYOUT objects** are fine. Examples:
  - A FreeCAD R14 file has OBJECTS with only ACAD_GROUP, no BLOCK_RECORD 340, and LTYPE records owned by the VPORT handle (cad-viewer#271, "Failed to open").
  - The tarikjabiri minimal AC1021 file **opens in AutoCAD** with an empty CLASSES section, no LAYOUT and no `$DWGCODEPAGE` (tarikjabiri-dxf#74 samples, sample-checked).
  - Synthesise `*Model_Space`, `*Paper_Space` and the layouts. VERIFIED-BY-ACAD (the minimal file opens)
- **Symbol table names.** Trim whitespace and compare case-insensitively ("PLATE" vs "plate " after xref merges; AutoCAD treats them as one layer) (cad-viewer#409, realdwg-web#pr131). Entities may sit on layers missing from the LAYER table, even layer `0` (freecad#20195, #19709). REPORTED
- **Entity type names beyond the basic set.**
  - `ARC_DIMENSION` is its own type name (AutoCAD 2004+).
  - `3DLINE` is the R10 name.
  - `HELIX` is a SPLINE subclass. These three were silently dropped, and LibreDWG `2007_Helix.dxf` opened blank (realdwg-web#pr170).
  - `MLEADER` and `MULTILEADER` both occur (dxf-viewer#170).
  - `AcDb2LineAngularDimension` (points 13-16) is written by AutoCAD 2025 but absent from the DXF reference (dxf-json#106).
  - VERIFIED-BY-ACAD (AutoCAD-written)
- **AutoCAD 2018+ MTEXT can carry a trailing `101 Embedded Object` section.** It reuses codes 10/11/40/41/46/70 and overwrote the real insertion point in dxf-parser and ixmilia. **Stop interpreting at `101`** (dxf-parser#pr41, ixmilia-dxf#195). REPORTED (confirmed on AutoCAD 2018 files)
- **MTEXT group 46** (defined annotation height) is always written by AutoCAD 2015 and LT 2020, between 41 and 71; 0 means auto. It is undocumented (ixmilia-dxf#185). VERIFIED-BY-ACAD
- **AutoCAD 2025 DIMENSION** writes DIMSTYLE overrides both as `ACAD` DSTYLE xdata and as raw codes (73/74/75 = DIMTIH/DIMTOH/DIMSE1) directly in `AcDbDimension` (dxf-json#94). VERIFIED-BY-ACAD (AutoCAD-written)
- **Rotated dimension subclass order.** AutoCAD and QCAD write the 13/14 definition points under `100 AcDbAlignedDimension`, then `100 AcDbRotatedDimension` with 50/52 (realdwg-web#pr176). A reader that seeks the leaf marker first loses the points. REPORTED
- **Other object quirks.**
  - AC1032 `SPATIAL_INDEX` has several 40s after the timestamp (ixmilia-dxf#159).
  - `SPATIAL_FILTER` has 12 or 24 40s, depending on the front-clip flag (ixmilia-dxf#192, dxf-json#76).
  - `MENTALRAYRENDERSETTINGS` codes don't match the spec (ixmilia-dxf#171).
  - `MLINESTYLE` element lists can have unequal lengths (ixmilia-dxf#96).
  - Parse objects leniently or skip them; nothing visual depends on these. REPORTED

## 3. Text encoding, codepages, CJK

- **The rule that holds in practice.** Files **< AC1021** hold **raw bytes in `$DWGCODEPAGE`**. **AC1021+ is UTF-8.**
  - dxf-viewer#135 is the proof:
    - `J0-J17.dxf`: R2013, MicroStation v8i, declares ANSI_936, bytes are UTF-8.
    - `line.dxf`: R2004, declares ANSI_936, real GBK.
  - FreeCAD `Encoding-error.dxf` (R13, `ansi_1252`): a raw 0xB0 byte, which **AutoCAD shows as "°"**, while bytes C2 B0 show as "Â°" (freecad#8704).
  - VERIFIED-BY-ACAD (freecad#8704 screenshot)
- **Declared codepages lie, both ways.**
  - Lies in pre-2007 files:
    - QGIS 4.2 writes UTF-8 MTEXT bytes while declaring AC1018 + ANSI_949. ARES Commander 2027 honours the codepage and shows mojibake (qgis#67573).
    - Teigha/ODA DWG→DXF: UTF-8 layer names with ANSI_1250 declared (qgis#20198).
    - UTF-8 with ANSI_1251 declared (gdal#3716, #13224, #11591).
  - Lies in AC1032 files: UTF-8 is correct but ANSI_936 is still declared (three-dxf#47 `left5.dxf`). That is harmless under the version rule.
  - **Heuristic: pre-2007, try strict (`fatal: true`) UTF-8 on the high-byte strings. Fall back to the codepage. Allow a user override** (realdwg-web#pr215 does "hybrid UTF-8/$DWGCODEPAGE detection"; dxf-viewer#135). ASSUMPTION, strongly supported by REPORTED cases.
- **Codepage name spellings.**
  - `ANSI_1252` and `ansi_1252` (AutoCAD R13) both occur.
  - QGIS writes non-standard `8859_1` (freecad#21905).
  - QGIS sometimes writes an **empty** `$DWGCODEPAGE` (qgis#60802).
  - `ANSI_949`/CP949 maps to WHATWG `euc-kr` (realdwg-web#pr207, cad-viewer#641).
  - GBK/GB2312 is `ANSI_936`; TextDecoder accepts `gbk`.
  - REPORTED
- **Mixed encodings in one pre-2007 file.** In `Drawing1.dxf` (AC1015, ANSI_936):
  - MTEXT uses `\U+5899\U+677F`.
  - STYLE/DIMSTYLE names are raw GBK (仿宋_GB2312, 标注, 1比10).
  - The exploded variant `NoNoHatchMtext.dxf` has raw-GBK TEXT (three-dxf#41, #42, sample-checked).
  - Decode all byte strings with the codepage, then expand `\U+XXXX` in **every** string field. That includes layer, block and dimstyle names; a layer needs a display name separate from its reference key (dxf-viewer#17, #31, #32). REPORTED
- **`\U+XXXX` takes exactly 4 hex digits.** `\U+22054.0通` must give "∅4.0通"; a greedy parser produced "??.0通" (cad-viewer#615). REPORTED
- **`\M+nXXXX` (MIF) occurs in real AutoCAD MTEXT** for bigfont SHX text, mixed with `\U+`. Example: `\M+1928D:\M+18DD1\M+197702.0t\U+9540…` (cad-viewer#2).
  - The digit n selects the codepage, as implemented by dxf-viewer:

    | n | Encoding |
    |---|---|
    | 1 | shift_jis (932) |
    | 2 | big5 (950) |
    | 3 | euc-kr (949) |
    | 4 | johab (1361); browsers cannot decode it |
    | 5 | gbk (936) |

  - Codes < 0x80 are ASCII. Split the hi/lo bytes and decode with `fatal: true`.
  - dxf-viewer code; cad-viewer#2; dxf-viewer#153. REPORTED. **UNKNOWN / needs AutoCAD test** for the n→codepage mapping.
- **Bigfont GBK round trip.** When a font lookup encodes a Unicode char to GBK for a bigfont, iconv-style encoders silently return `?` for unmappable characters.
  - Result: the auto-diameter sign **U+2205** (the glyph lives in amgdt.shx) was drawn as a literal `?` via hztxt.shx (cad-viewer#473).
  - Check encode→decode round-trip before accepting a bigfont glyph. REPORTED
- **Raw newlines and tabs inside MTEXT content** (from libredwg DWG conversion) must become `\P` and a space. mtext-parser dropped the **word before** a raw `\n` ("GR. 1,5 mm" became "GR. 1,5") (realdwg-web#221). REPORTED
- **Chinese producers ship proxies.**
  - Tianzheng (天正 TArch) walls and dimensions exist only as `ACAD_PROXY_ENTITY` / TCH_* classes. `left5.dxf` has 88 CLASS records including `TCH_KERNAL|缺乏解释器天正图形看不见, 请下载天正插件` ("graphics invisible without plugin") (three-dxf#47 sample; cad-viewer#51, #90, #619, #686; dxf-viewer#35).
  - Render proxy graphics (92/160 byte count + 310 chunks, concatenated) (dxf-json#pr115, realdwg-web#pr107). REPORTED
- **Where the non-ASCII text shows up.**
  - Most encoding bug reports come from CJK (Chinese, Korean), Cyrillic (Serbian, Russian), Polish, Hungarian, German and French users (qgis#19840, #51013, #30267; ixmilia-dxf#107, #153).
  - Codepage-dependent characters occur in TEXT, MTEXT, DIMENSION text, ATTDEF/ATTRIB, and in layer/block/style names (freecad#8704, qgis#20198, dxf-viewer#32).
  - REPORTED

## 4. Header variables, extents, initial view, units

- **Never trust `$EXTMIN`/`$EXTMAX`.** Observed values:
  - `+1e20`/`-1e20` inverted sentinels (QCAD AC1027, others; bjnortier-dxf#26, dxf-parser#27);
  - `±1e20` from OnShape (three-dxf#3);
  - `0,0` from Inventor;
  - stale values (qgis#14761: QGIS wrote 30..130 for data at 290,000..785,000; OOo Draw, Inkscape and CorelDRAW fit to those);
  - outlier-ridden values (cad-viewer#153, #347, #631).
  - Compute from geometry, excluding RAY/XLINE. REPORTED
- **Initial view from VPORT `*ACTIVE`.**
  - 12/22 is in **DCS**, relative to target 17 and rotated by twist 51: `WCS centre = target + rot(centre, twist)`.
  - Real DWGs store target (750984, −1587549). Ignoring it frames empty space about 1.9M units away (realdwg-web#pr138, cad-viewer#423).
  - Sanity-check stale saved views against geometry extents (realdwg-web#pr113).
  - VPORT view height 40 = 0 or Infinity occurs (tarikjabiri-dxf#77, #78, #146); clamp it.
  - AutoCAD **refuses to open** files with VPORT 40 = 0 (tarikjabiri-dxf#77). VERIFIED-BY-ACAD
- **Paper-space zoom chain.** Use the limits only when they contain the viewports; the bogus default `(0,0)-(12,9)` is common. Then try the viewports bbox, then layout extents, then fit (cad-viewer#284). REPORTED
- **`$INSUNITS` / `$MEASUREMENT`.**
  - GDAL/QGIS hard-code `$MEASUREMENT 0` / `$INSUNITS 1` (inch) whatever the CRS. FreeCAD then scales imports wrongly (qgis#50579, #22479; gdal#11423).
  - FreeCAD's precedence after many bugs: user override → INSUNITS (if ≠ 0) → MEASUREMENT → unitless (freecad#6461, #11394, #11729).
  - Yorik: many AutoCAD users never change INSUNITS from the template default (freecad#10253).
  - **A PLOT-matching renderer must never rescale model space by INSUNITS.** Units matter only for measurement readouts and plot scale. ASSUMPTION
  - `$MEASUREMENT` does select metric vs imperial *hatch patterns and linetypes*. dxf-viewer's code comments note `$MEASUREMENT` was wrong (25.4×) in 6 corpus files (dxf-viewer#36, #52). REPORTED
- **Bug classes when scaling units.**
  - Bulge (42) is dimensionless, yet FreeCAD multiplied it by the unit scale (freecad#13600).
  - TEXT height got a spurious pt→mm ×0.3528 (freecad#22779, #24859).
  - Keep the parser raw: no unit or angle conversion (dxf-parser#91 and three-dxf#18 confused users by converting ARC degrees to radians). REPORTED
- **`MIRRTEXT`.** GDAL's header has `$MIRRTEXT 1`. It only affects newly mirrored text in the editor (gdal#6018). **UNKNOWN / needs AutoCAD test**: does MIRRTEXT affect how existing mirrored INSERTs with text plot? REPORTED
- **`VIEWRES` is often stored as 1000.** Don't drive tessellation from it; the GPU memory and HTML export size explode (realdwg-web#pr192). REPORTED

## 5. Colour, layers, visibility

- **Absent 62 means ByLayer.** Libraries that defaulted to CECOLOR or ByBlock made whole drawings monochrome. LibreDWG `dwg2dxf` omits 62 on most entities and writes `$CECOLOR 0` (cad-viewer#521, realdwg-web#pr190, dxf-viewer#114, #122). An absent 8 means layer `0` (dxf-viewer#138). REPORTED
- **`420 0` after a real `62` is a writer bug. Keep the ACI.** Sources:
  - deskproto.com CNC samples (`62 18` + `420 0` on all 96 entities);
  - QCAD templates, dxflib samples;
  - bjnortier `1x1rectangle.dxf` (on LAYER records).
  - Read literally, it gives a black layer on a black background, i.e. an empty drawing. **11 of 17** such blank drawings in a 2,547-file corpus were fixed by this rule (realdwg-web#pr173). A lone `420 0` is still black. REPORTED
- **ByBlock at the top level (no INSERT owner) displays as ACI 7 / foreground.** dxf-viewer#160 had 658 such entities (VERIFIED-BY-ACAD). realdwg-web#pr160 uses the same rule. FreeCAD reports colour 0 outside a block as black (freecad#16632).

- **Layer on/off/frozen.**

- **Group 60 = 1 means invisible.**
  - Dynamic-block exports put each visibility state in an anonymous `*U` block, with hidden parts flagged 60 (dxf-viewer#115).
  - Honour it at the top level and inside blocks (realdwg-web#pr95, cad-viewer#320).

## 6. OCS / extrusion (210/220/230): the most common geometry bug in JS viewers

- **Extrusion (0,0,-1) is everywhere.** Sources:
  - MIRROR in AutoCAD R2018 (`V-plan1.dxf`);
  - netDxf ARC handle 28 at OCS centre (−30.906, −35.906), start 180 / end 270;
  - Proliner (a kitchen measuring system);
  - laser parts;
  - `Seite.dxf` (29 entities).
  - Ignoring it mirrors arcs and circles in x (three-dxf#92, dxf-parser#109, bjnortier-dxf#42, ixmilia-dxf#105, #203, freecad#17046). REPORTED; bjnortier-dxf#142 is VERIFIED-BY-ACAD (AutoCAD screenshot)
- **Which coordinates are OCS.**
  - **CIRCLE/ARC centres and LWPOLYLINE vertices (+38 elevation) are OCS.** 2D POLYLINE, TEXT, INSERT, SOLID, TRACE and HATCH are OCS too (spec).
  - **ELLIPSE 10/11 are WCS.** Only the parametric direction reverses: minor = N × major, which flips the 41→42 sweep.
  - `V-plan1.dxf` shows both: 43 CIRCLEs and 117 ELLIPSEs with 230=−1. The circle x values (−44290) land inside the LINE x-range only after negation, while the −Z ellipse centres already equal the +Z circle centres (bjnortier-dxf#142, sample-checked; troter's TrueView 2022 notes in bjnortier-dxf#80 agree).
  - VERIFIED-BY-ACAD. bjnortier's code comment "empirically flipping does not apply to polyline" was wrong for LWPOLYLINE (bjnortier-dxf#147).
- **Arbitrary normals.**
  - dxf-viewer only mirrors for Z<0 (dxf-viewer#105: 210 ≈ (0.008, −0.174, 0.985), with elevation).
  - **LibreCAD and QCAD show "many strange circles" for CIRCLE/ARC in tilted planes; a user with AutoCAD saw correct 3D geometry** (freecad#22124). VERIFIED-BY-ACAD. Implement the full Arbitrary Axis Algorithm.
  - realdwg-web had the OCS basis matrix transposed, which broke non-axis-aligned normals (realdwg-web#pr182).
- **Extrusion `(0,0,0)`** is written by LibreCAD on every SPLINE (`weird-splines.dxf`, `spline-slots-2000.dxf`). Treat it as +Z (bjnortier-dxf#50, freecad#21205, sample-checked). REPORTED
- **Mirrored INSERTs.**
  - Seen: INSERT with 43=−1 and 230=−1, rotation 270 (AutoCAD 2018, `left5.dxf`) (three-dxf#47). `41=-1500, 42=1500, 43=-1500, 50=270`: **negative 43 must be ignored for 2D; only 41/42 and 210 matter** (dxf-viewer#pr7). VERIFIED-BY-ACAD
  - Use `M = OCS(N) · T(ins) · R(rot) · S(sx,sy,sz) · T(−base)`, then flatten Z for plan view.
  - A negative determinant flips triangle winding, and FrontSide culling hid the fills (cad-viewer#183, #206, #645; VERIFIED-BY-ACAD by comparison). `THREE.Matrix4.decompose` breaks with mirrored or zero scale; keep the exact 4×4.
- **Zero INSERT scale.** INSERT `43 = 0` is written by bjnortier samples and much of LibreCAD's symbol library. The matrix becomes singular → `decompose` divides by 0 → NaN in every vertex/bbox → **blank drawing** (realdwg-web#pr175). Coerce 0 to 1; negative stays. REPORTED
- **Elevated inserts.** Title-block stamps at |Z| ≈ 9000 and MTEXT at large Z fall outside an ortho camera's near/far planes (realdwg-web#pr202, cad-viewer#368). Flatten Z (plan-view projection) before the GPU. REPORTED

## 7. Blocks, INSERT, attributes, dynamic blocks, xrefs

- **Attributes are essential to users.** The "missing text" in the Austrian cadastre (BEV DKM) was block ATTRIBs (Grundstücksnummern), compared against TrueView (qgis#27800). Title-block text went missing in ezdxf R2007 files (cad-viewer#243, VERIFIED-BY-ACAD vs AutoCAD 2016). Attach ATTRIBs to their INSERT via the 66=1…SEQEND sequence and owner 330, not by block name (dxf-viewer#58, #63). REPORTED
- **ATTDEF drawing rules.**
  - Rules (realdwg-web#pr154, #pr197; gdal#pr7723):
    - A loose ATTDEF in model or paper space shows its **tag**.
    - A **non-constant ATTDEF inside a block is not drawn**; the INSERT's ATTRIB supplies the value.
    - A **constant ATTDEF** (70 bit 2; used by dynamic blocks) draws its default.
    - An invisible one (70 bit 1) is never drawn.
  - SolidWorks writes real values into ATTDEF defaults. Drawing the ATTDEFs doubled the title-block text (cad-viewer#546).
  - REPORTED; **UNKNOWN / needs AutoCAD test** for the constant-ATTDEF case.
- **Invisible ATTRIBs** (70=1): `Network.dxf` has 22,710 invisible GIS_ID attributes (three-dxf#24). REPORTED
- **Fit-aligned ATTRIB (72=5).** The stored 41 is AutoCAD's computed result (`sss111.dxf`: ATTDEF 41=1.0417, ATTRIB 41=0.5515) (dxf-parser#118, sample-checked). ASSUMPTION: AutoCAD recomputes it from the alignment points at regen.
- **Dynamic blocks.**
  - The INSERT names an anonymous `*U` representation.
  - Resolve the original name via `AcDbBlockRepBTag` XDATA or the INSERT extension dictionary (dxf-parser#65, realdwg-web#pr211).
  - Render the `*U` block as-is; it is AutoCAD's evaluated geometry.
  - An unresolved nested `*U` reference crashed dxf-viewer's build (dxf-viewer#48). Warn and skip.
  - REPORTED
- **Tables.** Render `ACAD_TABLE` from its anonymous `*T` block, which holds AutoCAD's final geometry. Rebuilding from cell data gave cumulative row-position errors (realdwg-web#pr81). REPORTED
- **MINSERT.**
  - Codes are 70/71 (columns/rows) and 44/45 (spacing).
  - LibreCAD writes MINSERT as a plain INSERT with 71=14, 45=−0.5, nested.
  - Tested in LibreCAD only, the grid rotates with 50 but **is not scaled** by 41/42 (bjnortier-dxf#58, #59, sample-checked). **UNKNOWN / needs AutoCAD test**.
  - INSERT 70/71 = 0: **AutoCAD treats 0 as 1**; LibreCAD treats it as 0. Seen in a Chinese AutoCAD-like file with block 交换器 at −29,396,524 (gdal#11591, #pr11682, atlight). VERIFIED-BY-ACAD (atlight)
- **Xrefs.**
  - BLOCK flags 4/8 plus path 1. Flags 32/64 are AutoCAD-internal; an attached xref is often written with flag 36 (realdwg-web#pr147, #pr158).
  - An xref-heavy drawing had 37.5% top-level INSERTs (cad-viewer#422, #457).
  - For truedxf: draw unresolved xrefs as nothing and report them. ASSUMPTION
- **Instancing wins.**
  - The 16,359-entity block 会展-1F平面图, inserted 3×, cost **2.8 GB** RAM for a 4.9 MB DWG without instancing (cad-viewer#15).
  - FreeCAD's new importer builds a BLOCK once and links each INSERT to it (freecad#22045).
  - Unreferenced block definitions and nested blocks are very common (freecad#21962).
  - REPORTED
- **Fonts in blocks.** TEXT/DIMENSION inside BLOCKs was lost or misplaced in FreeCAD (a drill-log file compared against the AutoCAD DWG viewer, freecad#27371). Apply the full INSERT transform to text height, rotation and oblique. VERIFIED-BY-ACAD (viewer)
- **Lineweight is not scaled by INSERT scale.** A ×1000 INSERT turned SVG stroke width 0.1% into giant black blobs (bjnortier-dxf#63). ASSUMPTION: PLOT draws lineweights in paper units whatever the INSERT scale.

## 8. Polylines, widths, bulges, SOLID/TRACE, meshes

- **Closing-segment bulge.**
  - The bulge on the last vertex of a closed polyline was dropped (LibreCAD `myfirstdxf.dxf`, four rounded corners; bjnortier-dxf#21).
  - A 2-vertex closed polyline with a bulge, i.e. a near-full circle, was mis-tessellated as a tiny arc because of a CW/CCW angle-normalisation bug (gdal#1839, **renders as a circle in AutoCAD 2019**).
  - VERIFIED-BY-ACAD (gdal#1839)
- **Closing a polyline.**
  - LWPOLYLINE 70 is a bit field (129 = closed + plinegen; dxf-parser#19).
  - A closed polyline does not repeat its first vertex. After arc tessellation, snap the closing point exactly (gdal#pr10209: an 8-digit Gauss-Krüger `40585366.70650577` gave a non-closed ring).
  - REPORTED
- **Single-vertex closed LWPOLYLINE** (9 in one AutoCAD file) opens in AutoCAD and LibreCAD (bjnortier-dxf#20). **UNKNOWN / needs AutoCAD test**: what does PLOT draw, a dot or nothing?
- **Wide polylines.**
  - Constant width 43 applies when a vertex omits 40/41.
  - **TrueView renders it; LibreCAD, QCAD CE, FreeCAD and GDAL do not** (freecad#6112 PCB tracks, `43=0.3`; gdal#3636).
  - Render as filled area. A closed wide polyline is a *ring*, outer plus inner loop, not a self-intersecting stitched loop (realdwg-web#pr65, #pr217, #pr130).
  - Tapers to 0 give valve triangles. An arc whose width ≥ 2r collapses to a solid disk (realdwg-web#pr208).
  - Wide polylines are among the most-requested missing features in dxf-viewer (#45, #88, #130).
  - VERIFIED-BY-ACAD (TrueView)
- **Negative constant width.** QGIS writes `43 -1.0`, which SketchUp imports as a double line with a face (qgis#38513). Treat width ≤ 0 as 0. ASSUMPTION
- **Old-style POLYLINE/VERTEX/SEQEND** is written by QCAD/dxflib, Rhino, Illustrator and many GIS tools, often inside blocks (ixmilia-dxf#65, dxf-parser#pr20).
  - VERTEX 41 fell through into 42 in dxf-parser, so bulge = end width (dxf-parser#50).
  - LWPOLYLINE group 91 (vertex id; ezdxf R2013) dropped vertices in dxf-viewer (dxf-viewer#100).
  - REPORTED
- **Curve/spline-fit POLYLINE** (70 bits 2/4). dxf-viewer renders only the fit vertices (dxf-viewer code). ASSUMPTION: AutoCAD renders the generated spline-fit VERTEXes (70 bit 8); skip the frame (bit 16) vertices.
- **Vertex order.**
  - SOLID/TRACE store corners 1-2-4-3. Drawing 1-2-3-4 gives a bow-tie (three-dxf#pr13, realdwg-web#pr90, cad-viewer#291, #657).
  - A 3DFACE/quad has no reliable triangulation; don't add triangles (dxf-viewer#74, #92). REPORTED
- **Polyface mesh** (70 bit 64).
  - Indices 71–74 are **1-based** (cad-viewer#150); a negative index marks an invisible edge.
  - Revit 3D export uses polyface meshes (dxf-viewer#40).
  - "Old AutoCAD DXFs sometimes encode outlines as polyface meshes" (bjnortier-dxf#138).
  - An empty mesh bbox → Infinity → NaN viewBox (bjnortier-dxf#51).
  - REPORTED

## 9. Arcs, ellipses, splines

- **Arc angles.**
  - ARC end angles > 360° occur: ezdxf-written from Cadkey97 (freecad#10985, #11002).
  - Angles are always degrees in the file; ELLIPSE params and HATCH ellipse edges are radians (ixmilia-dxf#139).
  - A hatch full-circle edge written as 50=0 / 51=0 (after 2π→0 normalisation) makes **AutoCAD and ezdxf treat the loop as open and drop the fill**; 110 solid circles came out hollow (realdwg-web#203, #pr204, #pr206). The same happens for full-ellipse edges.
  - REPORTED
- **Spline producers break naive evaluators.** three-dxf's Bézier hacks failed on all of these:

  | Producer / file | What it writes | Source |
  |---|---|---|
  | Inventor | Arcs and circles as cubic SPLINEs, 70=8, doubled interior knots, no weights | three-dxf#8 |
  | Rhino | Circles as **rational degree-2** splines | three-dxf#18 |
  | QCAD | Fit-point splines, 70=1064, with un-normalised knots 0..5015 | dxf-parser#27 |
  | `SPLINE3.dxf` | Closed periodic, 70=11 | three-dxf#34 |
  | LibreCAD | 70=11 (closed+periodic) with **clamped** knots and interior multiplicity = degree+1; FreeCAD drew a seam glitch, LibreCAD and BricsCAD are fine | bjnortier-dxf#50, freecad#21205 |

  - Implement real de Boor/NURBS with weights (41) and arbitrary knots, and evaluate the knots as given; the periodic flag is secondary. REPORTED
  - dxf-viewer ignores weights, so conics come out wrong (dxf-viewer#175).
  - A rational "squircle" circle is rendered squarish by "most CAD programs I tested" (bjnortier-dxf#65). **UNKNOWN / needs AutoCAD test**.
- **Missing weights.** A rational spline without its 41 weights was wrong in AutoCAD: degree 2, knots [0,0,0,1,2,2,2], weights [1,10,10,1] (tarikjabiri-dxf#40). VERIFIED-BY-ACAD
- **Fit-point-only splines** (11/21/31 + 12/13 tangents, no control points or knots) are written by Aspose.CAD. **AutoCAD reads them fine** (atlight, gdal#10397). Major CADs always also write control points. Implement global interpolation. REPORTED
- **Knot vector cases.**
  - Knots sometimes start with a tiny negative value (−3.4e−13), and one file had a knot/control-count mismatch; it still renders in TrueView 2020 and AutoCAD 2018 (gdal#1969). VERIFIED-BY-ACAD
  - Spline without knots: GDAL recalculates uniform clamped knots (gdal#pr115).
  - Numeric drift: clamp t to [0,1] (bjnortier-dxf#28, `1.0000000000000002`).
  - Real splines have hundreds or thousands of control points; interpolating 1579 leader fit points with a dense solver timed out (gdal#502). Use a banded solver (realdwg-web#pr215).
  - REPORTED
- **Closed flag vs geometry.** 775 of 809 SPLINEs in one file have first == last control point but 70 bit 1 = 0, and AutoCAD shows them closed (ixmilia-dxf#190). Render the geometry as given; the flag doesn't change it. REPORTED
- **Splined LEADER** (72=1) with the usual **3 vertices** (76=3) needs a degree fallback. A degree-3 spline needs 4 points; realdwg-web threw and dropped the leader (realdwg-web#pr174, LibreDWG `*_Leader.dxf`). REPORTED

## 10. TEXT, MTEXT, fonts

**TEXT placement**

- **TEXT anchor rule: with 72/73 ≠ 0, the anchor is 11/21, not 10/20.**
  - Group 10 is AutoCAD's computed left-baseline, from AutoCAD's own font metrics.
  - A renderer with different metrics must anchor at 11 (gdal#1779, realdwg-web#pr77, QCAD does it; gdal#pr225: AutoCAD's "Text alignment X/Y" property equals 11/21). VERIFIED-BY-ACAD
  - **Track whether 11 was present, not whether it equals 10.** ezdxf `set_placement` writes 10 == 11, and so does AutoCAD when the points coincide. A viewer treated 10 == 11 as "unset" and shifted all centred text (realdwg-web#199, #pr200). REPORTED
  - Writers that set 72 but omit 11: **AutoCAD puts the text at (0,0)** (tarikjabiri-dxf#34, ixmilia-dxf#181). VERIFIED-BY-ACAD
  - halign 4 (MIDDLE) collapses to middle-center. Baseline and Bottom differ for fonts with descenders; the SHX descender is about 0 (realdwg-web#pr77). REPORTED
- **TEXT rotation 50 is in degrees.** FreeCAD first ignored it, then used radians: BricsCAD texts at 0/90/180/270 came out at "random" rotations (freecad#10882, #21548). REPORTED

**MTEXT**

- **MTEXT direction.**
  - 11/21/31 is a **unit direction vector**, not an offset. atlight compared the atan2 with AutoCAD's Rotation property: (0.082, −0.997) → 274.7° (gdal#pr225).
  - AutoCAD writes 11/21, not 50 (ixmilia-dxf#184).
  - If both are present "the last one wins" (spec).
  - VERIFIED-BY-ACAD
- **MTEXT content.**
  - Group 3 chunks of 250 characters come **before** group 1; concatenate the 3s in order, then the 1.
  - At least four libraries got this wrong: dxf-parser#36, dxf-json#11, freecad#8968 (kept only len mod 250; the fix was later reverted by another PR and re-applied), three-dxf.
  - REPORTED
- **MTEXT line spacing.** Pitch = 5/3 × height × factor (44, default 1.0) (realdwg-web#pr157, dxf-viewer code). 73 = 1 is "At Least": it expands only when the factor would pack lines tighter than the text height. 73 = 2 is Exact (realdwg-web#pr216). REPORTED
- **MTEXT wrapping.**
  - **A single word wider than the box spills outside it. A space before that word makes an empty line and pushes the word down** (dxf-viewer#160, VERIFIED-BY-ACAD; 71 narrow MTEXT, width ≤ height).
  - CJK text may break between any two characters, with kinsoku punctuation rules (dxf-viewer#149).
  - For CJK MTEXT with 41 < height, cad-viewer estimated the width from the longest `\P` line (cad-viewer#264). REPORTED. **UNKNOWN / needs AutoCAD test** for AutoCAD's own behaviour.
- **MTEXT attachment (71).** Apply it exactly once; a duplicate top shift pushed title-block fields too low (cad-viewer#269). The leader hook line uses the MTEXT actual extents (realdwg-web#pr133). REPORTED
- **Inline codes seen in real files.**
  - `\A1;` prefix on every MTEXT (AutoCAD R2000 CJK).
  - `{\fArial|b0|i0|c0|p34;…}` (three-dxf#68).
  - `{\fArial Unicode MS|b0|i0|c136|p34;…}`.
  - `\f나눔고딕|i0|b0;\H2.97656;` (QGIS).
  - CJK table cell `\A1;{\H0.7x;\S开^ 终;}孔日期` (dxf-viewer#164). The space after `^` is part of the stack encoding.
  - `\C6;` (dxf-viewer#160, VERIFIED-BY-ACAD).
  - Field codes `%<\AcVar ViewScale …>%` in left5.dxf. Render the cached evaluated text (ASSUMPTION).
  - dxf-viewer ignores `\f \H \W \Q \T \L \O \K` and flattens scopes. Lowercase `\c` (true colour) is not handled and would be printed literally (ASSUMPTION from code).
  - Inline `\C` colours in ACI-7 MTEXT must not flip with the background (cad-viewer#466).
  - Don't strip codes with a regex; `xqc;` leaked through (cad-viewer#642).
  - REPORTED
- **MTEXT features in the wild.**
  - Columns: only about 10 of the dxf-viewer maintainer's "hundreds" of real files use them, all single-column (dxf-viewer#104, which has an AutoCAD reference image).
  - Background fill: the box size looks undocumented (dxf-viewer#88).
  - **Writing 63/420-441 background codes while 90 = 0 made AutoCAD 2015 fail with "Missing DXF group code: 90 … drawing discarded"; AutoCAD Viewer 2020 is stricter still** (ixmilia-dxf#179). VERIFIED-BY-ACAD
- **Special codes.**
  - `%%d` → °, `%%p` → ±, `%%c` → ⌀ (dxf-viewer maps it to U+2205).
  - AutoCAD's *auto-generated* dimension diameter sign is **U+2205** (the glyph is in amgdt.shx) (cad-viewer#473).
  - `%%o`/`%%u` toggle overline and underline (unimplemented in dxf-viewer).
  - The inch sign `"` rendered as `4` in cad-viewer (cad-viewer#285, VERIFIED-BY-ACAD by comparison).
  - REPORTED

**Fonts**

- **The font problem is the #1 text complaint.**
  - Missing Chinese SHX/TTF: simsun, tssdeng, tssdchn, hztxt, gbenor+gbcbig, gbhzfs, rex, hz, allinonebig…
  - Missing GOST fonts rendered as `?`.
  - A `times` substitute made text "surprisingly large" (cad-viewer#29, #246, #571).
  - **AutoCAD 2026's fallback for a missing gost font is txt.shx** (cad-viewer#246, VERIFIED-BY-ACAD). truedxf should model FONTALT, then txt.shx, for PLOT fidelity.
  - STYLE xdata carries the TrueType family: `1001 ACAD / 1000 SimSun / 1071 34306`, where 34306 = 0x8602 looks like charset 0x86 = GB2312 plus pitch/family (tarikjabiri-dxf#72, sample-checked; bit layout is ASSUMPTION).
- **Font loading.**
  - Fonts must never block the open. A jsdelivr font CDN outage failed *every* open (realdwg-web#129); load on demand (#pr181).
  - A glyph baked before its font arrives stays `?` forever; rebuild on late load (cad-viewer#647, #658; three-dxf#96 needed a `setTimeout(render, 300)` workaround).
  - REPORTED
- **Text size and metrics.**
  - AutoCAD text height = cap height. QGIS computes the size from the tight bounding rect, "otherwise the text will be too big in the dxf" (qgis#pr7273).
  - dxf-viewer aligns CENTER/RIGHT/MIDDLE by the glyph *ink* bbox and admits its TTF scale `100/(unitsPerEm×72)` is "not really clear" (code). This is a likely mismatch against AutoCAD; SHX metrics are needed. ASSUMPTION
- **SHAPE entities and shape-file STYLEs.** SHAPE has no style reference, so search STYLE entries with 70 bit 1. A numeric name like `"9"` is a shape code (cad-viewer#113, #367, #434; realdwg-web#pr111). AutoCAD looks for the .shx next to the DWG. REPORTED
- **Rendering cost.** Triangulating TTF outlines is memory-heavy on text-heavy files; SHX strokes are much cheaper (dxf-viewer#55). Emit SHX pen-down runs separately; don't chain strokes (cad-viewer#643). REPORTED

## 12. Linetypes and lineweights

- **Not rendered at all** in dxf-viewer (dashes draw solid; dxf-viewer#144, #116, #130), three-dxf, or bjnortier (a fixed "5,5" for any non-Continuous linetype; bjnortier-dxf#98). This is a frequently reported "looks different from AutoCAD" item. REPORTED
- **Sub-cycle segments draw continuous.** A segment shorter than one pattern cycle draws as a continuous stroke, and TEXT/SHAPE elements are skipped (cad-viewer#668, via #285's AutoCAD comparison). VERIFIED-BY-ACAD. This is standard AutoCAD behaviour; PLINEGEN (70 bit 128) makes the pattern run continuously across vertices.
- **Scale factors.** Effective scale = LTSCALE × CELTSCALE × entity 48 × (PSLTSCALE rules in paper space). Ignoring LTSCALE/CELTSCALE was an early cad-viewer bug (cad-viewer#44, #53). The dxf-viewer PR #171 design (arc-length attribute + 16-slot pattern uniform) ignores LTSCALE, 48 and block scale (dxf-viewer#171). REPORTED
- **Complex TEXT/SHAPE linetypes** (GAS, FENCELINE1…).
  - Must read LTYPE 74/75/340/46/50/44/45/9 (realdwg-web#pr209). LibreDWG swaps 74/75 and blanks the texts (cad-viewer#651, #653).
  - Dense FENCELINE1 at a high LTSCALE exploded into millions of glyphs; cap by a cycle budget (cad-viewer#660).
  - REPORTED
- **GPU approach pitfalls.**
  - Shader-based dashes broke at zoom thresholds (cad-viewer#102).
  - Integrated AMD Radeon (ANGLE/D3D11) produced **zero fragments** with the pattern shader on `gl.LINES` (cad-viewer#545).
  - `mod()` on line distance needs highp (#555).
  - Recompute line distance after merging batches (#405, #650).
  - REPORTED
- **Lineweights.**
  - 370 is in 1/100 mm and shows only with `$LWDISPLAY` = 1 (tarikjabiri-dxf#138).
  - LAYER lineweight is **370**, not 390 (390 is the plot-style handle) (bjnortier-dxf#18).
  - Viewers default LWDISPLAY off because width quads cost frame rate (cad-viewer#170; realdwg-web#pr45). With it on, a frame and blocks vanished in one file (cad-viewer#112).
  - **For PLOT, lineweights always apply** (ASSUMPTION; plot uses lineweights or CTB regardless of LWDISPLAY). WebGL lines are 1 px, so widths need CPU-built quads (dxf-viewer#45).
  - REPORTED
- **Writer side.** GDAL output with `PEN(w:3g)` (lineweight) made AutoCAD 2015 refuse the file, while LibreCAD accepted it (gdal#835). VERIFIED-BY-ACAD

## 13. Dimensions, leaders, tables

- **Render the `*D` block named in DIMENSION group 2.** It is AutoCAD's pre-built geometry, drawn at identity transform. A DIMENSION's layer and colour propagate into it, and entities in `*D` blocks often have no 62, i.e. ByLayer (dxf-viewer#80, #122; three-dxf#85; bjnortier-dxf#10). REPORTED
- **Files without `*D` blocks exist.**
  - QCAD and others lay dimensions out at display time; `dimangular006.dxf` has only `*Model_Space` and `*Paper_Space` in BLOCKS. **23 of 2,547 corpus files open blank** for this reason alone (realdwg-web#pr177). A synthesiser is needed.
  - Synthesiser details:
    - Take DIMASZ and DIMTXT × DIMSCALE, DIMDEC and DIMLFAC from the style.
    - Substitute `<>` with the measurement. `" "` suppresses the text, `""` means use the measurement.
    - Measure a rotated dimension **along its dimension line**: a 30×10 offset reads 30, not 31.62.
    - Group 42 is a cached measurement, and QCAD writes −1 for "none".
  - **AutoCAD regenerates a model-space DIMENSION that has no group 2 and displays it** (tarikjabiri-dxf#74). VERIFIED-BY-ACAD
  - **A DIMENSION inside a BLOCK that references a non-existent `*D2` is invisible in AutoCAD** until the block is edited (tarikjabiri-dxf#75). VERIFIED-BY-ACAD
  - ixmilia also saw dimensions inside blocks not displayed (ixmilia-dxf#60).
  - Writing `2 = *MODEL_SPACE` as the dimension block name crashed AutoCAD (ixmilia-dxf#pr125). VERIFIED-BY-ACAD
- **DIMSTYLE text style.** A DIMSTYLE without 340 (DIMTXSTY) makes **dimension text vanish in AutoCAD** (tarikjabiri-dxf#74, sample pair). VERIFIED-BY-ACAD. So don't fall back to STANDARD when matching AutoCAD. ASSUMPTION
- **Arrowheads.** netDxf writes DIMSTYLE 342 = handle → BLOCK_RECORD `_ARCHTICK` with an empty `$DIMBLK`, and AutoCAD shows the architectural tick (dxf-viewer#80, sample-checked). REPORTED
- **DIMJUST 1/2** mean "next to the first/second extension line", not left/right (dxf-json#90). REPORTED
- **LEADER.**
  - 3 (dimstyle name) must name an existing DIMSTYLE, otherwise AutoCAD 2013 does not display the leader (tarikjabiri-dxf#41). VERIFIED-BY-ACAD
  - A splined leader has 3 vertices (§9).
- **MLEADER.** "The Autodesk DXF reference for this is poor and seems auto generated" (dxf-parser#pr94). Use atlight's leader write-up. Styles come from `MLEADERSTYLE`; colours are raw int32 (realdwg-web#pr72, #pr75). REPORTED
- **Precedence of dimension style values.** XDATA DSTYLE > entity-embedded codes (AutoCAD 2025) > DIMSTYLE > header (dxf-viewer#28, #33; dxf-json#94). REPORTED

## 16. Coordinate precision (float32 GPUs)

- **Coordinates are big.**
  - UTM / Gauss-Krüger / Lambert-93 / EPSG coordinates of 10⁶–10⁷ are the norm in GIS and survey files: 2.86e6/4.64e6 in `Network.dxf`, 40,585,366 in gdal#10153, 5.77e6 in freecad#5979, a Chinese file at −29,396,524.
  - Float32 destroys mm detail:
    - text becomes rectangles, circles jagged, symbols distorted, text blurry (cad-viewer#22, #36, #124, #157, #194: VERIFIED-BY-ACAD by screenshots);
    - three-dxf was visibly wrong vs AutoCAD (three-dxf#24, VERIFIED-BY-ACAD);
    - "the Autodesk online viewer also shows artefacts" (three-dxf#45).
  - **The fix:**
    - Keep a float64 model.
    - Compose block matrices in float64.
    - Subtract a render origin in float64 *before* uploading float32.
    - Split batches by origin.
    - Rebase text meshes, point symbols and hatch pattern bases.
    - Sources: dxf-viewer#4, #6; cad-viewer#157, #180, #354, #648.
  - cad-viewer's maintainer puts the threshold at "generally >10,000,000"; the batch-policy switch is at ≥1e6. REPORTED
- **A trap for instancing.** One unique block per GIS feature, each inserted at 0,0 with the geometry at UTM coordinates (`Network.dxf`, 22,710 blocks). Block-local coordinates are then huge too; rebase inside block definitions as well. REPORTED

**Architecture worth copying: dxf-viewer**

- Fetch, parse and scene build run in a Web Worker. Vertex, index and transform `ArrayBuffer`s return via the transfer list, zero-copy (dxf-viewer#108).
- Batch key: (layer, block, geometry type, colour, linetype). The maintainer: the bottleneck is draw calls, not primitives.
- Blocks are drawn with instanced geometry. A block is flattened instead when it is used once, or when useCount × vertices ≤ 1024.
- Vertices are 2D Float32 (saves 33%); indices are Uint16 in 64K chunks.
- Tessellation is fixed: 10° arcs (min 8 segments), splines at control points × 4. ASSUMPTION: this is too coarse or too fine for PLOT; use chord-height tessellation (realdwg-web#pr192).
- REPORTED

**Costs of batching**

- Draw order is lost (dxf-viewer#66).
- Entity identity is lost, so picking, highlighting and recolouring are impossible without a side index or ID buffer (dxf-viewer#16, #30, #158).
- Batching pitfalls:
  - entities added after load didn't appear until the camera moved;
  - `drawRange` exported deleted slots;
  - one NaN vertex emptied the spatial index (cad-viewer#286, #311, #370, #606).
- Filter NaN/Inf before the GPU.

**Worker and wasm deployment is the top integration pain**

- Relative worker URLs break with history routing.
- `file://` blocks module workers.
- A 13 MB wasm inlined as a data-URI crashed webpack.
- A GPL worker got bundled into apps that don't use DWG.
- Sources: cad-viewer#19, #52, #54, #494.
- Chrome allows about 16 WebGL contexts, so pages with many viewers lose contexts (dxf-viewer#147). Also `renderer.forceContextLoss()` on dispose (three-dxf#70).
- REPORTED

**Open pipeline and parsing**

- Progressive open with UI yields on a time budget (realdwg-web#pr161).
- Decode UTF-8 in 64 KiB windows aligned to line breaks, with no full-file string (realdwg-web#pr163).
- Transfer the input `ArrayBuffer` to the worker (realdwg-web#pr165).
- Worker timeout: 30 s base, scaled by size, capped at 120 s (realdwg-web#pr30).
- Skip converting off/frozen layers (cad-viewer#346).
- REPORTED

**Desktop tools make the same mistakes**

- The parser is never the bottleneck; creating one object per entity is.
- FreeCAD: 120 s → 4–5 s by batching layer assignment, which had been O(n²) (freecad#15732, #16596).
- Yorik: "the viewport handles millions of lines easily, the key is to have few objects".
- REPORTED

## 18. What AutoCAD refuses to open (writer lessons; readers must still tolerate these)

**Handles and object references**

## 20. What users of web DXF viewers want (ranked)

Sources: QGIS, GDAL, FreeCAD.

## 21. Maintainer lessons: copy / avoid

**Copy**

- **Scene model independent of the renderer.** DxfScene → three.js in dxf-viewer; parse → denormalise → `toPolylines()` → SVG/canvas backends in bjnortier (dxf-viewer#30; bjnortier-dxf#40).
- **Warnings instead of failures, exposed through an API**: counts of unknown and malformed entities; first-occurrence line number + handle per unsupported type. FreeCAD's import statistics report is the model (freecad#21985; bjnortier-dxf#20, #67; realdwg-web#pr171).
- **Raw values in the model**: raw colour index + RGB, raw angle units, XDATA as (code, value) tuples, points as `{x,y,z}` (dxf-parser#84, #pr34, #pr82).
- **One generic pair reader**, a header pre-scan for version and codepage, case-insensitive codepage aliases (freecad#9060, #9712, #11701).
- **A private corpus with recorded scene dumps as regression tests** (dxf-viewer test/). realdwg-web's 2,547-file and 661-file corpus scans found the blank-drawing classes: `420 0`, missing `*D` blocks, no subclass markers, `$HANDSEED` overflow, INSERT 43=0.

**Avoid**

- **Using a viewer as ground truth.** The Autodesk viewer ignored pattern scale/angle, failed to open some files, and had colour bugs (dxf-viewer#36, #114, #160).
- **Decoding text before reading the header** (dxf-viewer#72, #95).
- **Batching that loses draw order and identity** (dxf-viewer#66, #16).
- **Separate transform code per primitive.** This is the cause of bjnortier-dxf#42, #52, #142.
- **Handle-keyed maps.**
- **Unit or angle conversion in the parser.**
- **GPL dependencies and churn-prone three.js internals** (three-dxf#59, #90, #97).
- **AI-generated regressions without a corpus.** cad-viewer's maintainer says most recent code is Codex-written; there were frequent regressions (#89, #170, #259→#426, #667, #685).

## Test ideas

Small DXFs to pin behaviour down against AutoCAD **PLOT** (monochrome.ctb and no-CTB variants). Every file must first pass AutoCAD AUDIT/open (§18).

1. **OCS matrix.** CIRCLE, ARC, LWPOLYLINE (bulged, with 38 elevation), 2D POLYLINE, ELLIPSE (partial 41/42), TEXT, MTEXT, INSERT, SOLID, HATCH:
   - with 210 = (0,0,−1), each next to a +Z twin;
   - repeated with (1,0,0), (0,−1,0) and (0.577,0.577,0.577);
   - plus 210 = (0,0,0) on SPLINE/CIRCLE.
   - Pins the ELLIPSE-WCS vs CIRCLE-OCS difference (bjnortier-dxf#142, freecad#22124).
2. **Mirrored and odd INSERTs.**
   - 41=−1; 43=−1 with 230=−1 and rotation 270; non-zero base point.
   - INSERT 43=0; INSERT 70/71=0; a MINSERT with rotation and 41=2 (is the spacing scaled?).
   - Contents: an asymmetric block holding TEXT, ATTRIB, a solid HATCH and an ARC. Try MIRRTEXT 0 and 1.
3. **Colour and layer inheritance.**
   - Top-level 62=0 (ByBlock) with and without linetype ByBlock.
   - Absent 62; `62 18` + `420 0`; a lone `420 0`.
   - Layer-0 vs layer-A entities inside a block inserted on layer B, nested 2 levels.
   - Layer B off vs frozen; layer 0 frozen.
   - ACI 7 lines and ACI-7 solid hatch; ACI 1–255 swatch + 420 (pins the palette, dxf-parser#33).
4. **Plot visibility.** A no-plot layer (290=0), Defpoints POINTs with PDMODE=35, a viewport on a `*-NPLT` layer, group 60=1 in a top-level entity and in a `*U` block, an invisible INSERT.
5. **TEXT anchor matrix.** All 72×73 combinations:
   - with 11 == 10 present;
   - with 11 absent (expect (0,0));
   - with 10 deliberately "wrong";
   - Aligned (72=3) and Fit (72=5) with an inconsistent stored 41.
   - Glyphs with and without descenders, in both txt.shx and a TTF style.
6. **MTEXT.**
   - A 600-char MTEXT split 3,3,1, with the 250 boundary inside `\U+` and inside `\P`.
   - Direction vector (11/21) vs 50.
   - A word wider than the box, with and without a leading space; CJK wrapping with kinsoku punctuation.
   - Codes: `\A1;`, `{\fArial|b0|i0|c0|p34;…}`, `\H0.7x;`, `\S1^ 2;`, `\S1/2;`, `\S1#2;`, `\C1;`, `\c16711680;`, `^I`, `%%c`, `%%d`, `%%p`, `%%u`.
   - Line spacing 73 = 1/2 with 44 = 0.8 and 1.5.
   - Attachment 71 = 1..9 with and without width.
7. **Encodings.** The same text "°±Ø 墙板" as:
   - AC1015 raw GBK (ANSI_936);
   - AC1015 with `\U+`;
   - AC1015 with `\M+5xxxx`, also `\M+1`/`\M+2`/`\M+3` variants in a bigfont style;
   - AC1018 UTF-8 bytes declaring ANSI_936 (what does AutoCAD show?);
   - AC1027 UTF-8 declaring ANSI_936;
   - AC1015 `ansi_1252` raw 0xB0 vs C2 B0;
   - an empty `$DWGCODEPAGE`.
   - Pins the codepage heuristic and the MIF mapping (UNKNOWN items in §3).
8. **Fonts.**
   - A STYLE referencing a missing SHX, with and without FONTALT; record the substitute and advance widths.
   - Bigfont gbcbig with U+2205 in a diametric DIMENSION.
   - STYLE xdata TTF family (SimSun/34306).
9. **HATCH.**
   - ANSI31 with 41=2, 52=30 and correct embedded lines; the same with deliberately wrong embedded lines (which wins?).
   - QCAD placeholder single-45°-line definition with name ANSI31.
   - 75 = 0/1/2 × 3 nested loops × 92 flags.
   - SOLID with 3 disjoint loops: two touching at a corner (the LibreCAD gdal#9240 case), one with an island.
   - Full-circle arc edge as 0..360 vs 0..0.
   - A CW (73=0) arc edge.
   - A spline edge with weights.
   - 98 = 2 seed points.
   - A solid hatch created before vs after MTEXT, with and without SORTENTSTABLE.
   - The same hatch at (5e6, 5e6).
10. **Linetypes.**
    - DASHED on segments shorter and longer than one cycle.
    - LWPOLYLINE with and without PLINEGEN (70 bit 128).
    - LTSCALE × CELTSCALE × 48 × INSERT scale combinations; PSLTSCALE in a layout.
    - A complex text linetype (GAS_LINE) on short segments.
11. **Lineweights.** A 0.5 mm layer lineweight inside an INSERT scaled 1000×; LWDISPLAY 0 vs 1 (should not affect PLOT); ByBlock lineweight.
12. **Wide polylines.**
    - 43 constant width, closed and open, with bulges.
    - Per-vertex taper to 0.
    - Arc with width ≥ 2r.
    - `43 -1`.
    - Closed single-vertex LWPOLYLINE with width 0 and > 0.
13. **Splines.**
    - Rational quadratic circle (weights 1/√2).
    - Inventor-style cubic with doubled knots.
    - 70 = 11 with clamped knots vs a truly periodic knot vector.
    - Fit-point-only (no control points).
    - Knots 0..5000.
    - First == last control point with 70 closed bit = 0.
    - Splined LEADER with 3 vertices.
14. **Dimensions.**
    - DIMENSION with its `*D` block; with group 2 absent (model space); in a block pointing at a missing `*D`.
    - DIMSTYLE without 340.
    - Rotated dim with offset points (reads 30, not 31.62).
    - Text override `<>`/" "/"".
    - DIMSTYLE 342 → `_ARCHTICK`.
    - AutoCAD-2025-style inline 73/74/75 overrides.
15. **Attributes.** ATTDEF constant vs non-constant inside a block, a loose ATTDEF, ATTRIB 70 = 1, ATTRIB Fit, SolidWorks-style ATTDEF with a real default + ATTRIB.
16. **Tokenizer torture file** (parser-only; no AutoCAD needed):
    - 999 everywhere; unpadded and padded codes; `\r\r\n` and a lone `\r`; BOM; trailing newline after EOF.
    - `1.0E 20`, `inf.0`, `nan.0`, `2,5`.
    - Unknown codes 250/380/347; interleaved 10,11,20,21.
    - `1001` right after 3DFACE vertices; malformed `1002 {` without `}`.
    - Several 102 groups on a BLOCK_RECORD.
    - POLYLINE without VERTEX.
    - A header var with its group code missing.
    - A 5000-char `$CUSTOMPROPERTY`; `$HANDSEED D9B071D01A0CB6A8`.
    - No HEADER; no subclass markers; ENTITIES-only.
    - Binary DXF (R12 and R2018) and a DWG renamed to .dxf (must be *detected*).
17. **Initial view and extents.**
    - `$EXTMIN 1e20 / $EXTMAX −1e20`.
    - VPORT `*ACTIVE` with non-zero target 17 and twist 51.
    - VPORT 40 = 0.
    - Geometry at negative coordinates only.
    - AutoCAD PLOT "Extents" vs the viewer fit.
18. **Precision.** A 0.2-unit TEXT, a 1 mm circle, a dashed line and a patterned hatch at (3,026,284; 4,643,826), at 4.06e7, and at −2.9e7, in model space and in a block inserted at 0,0. They must be pixel-identical to the same drawing at the origin.
19. **Layouts.**
    - Default viewport plus user viewports numbered 0 and 1.
    - One viewport off, one twisted, one on a no-plot layer.
    - Bogus `(0,0)-(12,9)` limits.
    - Entities with 67 = 1 in two layouts.
20. **Performance baselines** (no AutoCAD needed):
    - 40k LINE (FortyThousandLines).
    - 22k unique blocks + ATTRIB (Network.dxf pattern).
    - A 16k-entity block inserted 3×.
    - 205k entities with XDATA.
    - A 400 MB synthetic file parsed without building one JS string.
    - Track peak heap and draw calls.
